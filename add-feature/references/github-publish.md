# GitHub公開手順

`add-feature` の承認ゲートでGitHub操作が承認され、実際にIssue、push、PR、マージを行う段階だけ参照する。

## 原則

- 承認された操作だけを実行する。
- リポジトリ固有の `AGENTS.md` とGit規約を優先する。
- 既定ブランチ、許可されたマージ方式、既存ラベル、CIを読み取り確認する。
- ユーザーの未コミット変更をstash、commit、破棄しない。
- Issue、PR、最終報告で同じ説明を繰り返さない。

## Issue

Issueが承認されている場合だけ作成する。本文は次に限定する。

- 変更の目的
- 主要な受け入れ条件
- 影響範囲の短い要約
- ステアリングディレクトリへの参照

存在するラベルだけを使い、ラベルを勝手に新設しない。Issue番号とURLを記録する。

## ブランチ

- 既定ブランチへ直接実装・commitしない。
- ブランチ名はリポジトリ規約、既存履歴、ホスト環境の規則の順で決める。
- 既定ブランチの最新化でユーザー変更と衝突する場合は実行せず、状況を報告する。
- ステアリングファイルは作業ブランチへ含める。

## Commitとpush

- `git status` と差分を確認し、今回の変更だけを明示的にstageする。
- `.env`、鍵、トークン、生成物、無関係なユーザー変更が含まれないことを確認する。
- commit形式はリポジトリ規約に従い、なければ既存履歴に合わせる。
- force pushしない。
- pushは承認されたブランチにだけ行う。

## PR

PR本文は次に限定する。

- 変更概要
- 主要な差分
- lint、型、テスト、実動作の結果
- Issueへのclose参照。Issueがない場合は省略

要求や設計の全文は転記せず、ステアリングを参照する。DraftかReadyかはユーザー要求とリポジトリ規約に従う。

## マージ

マージが承認されており、次をすべて満たす場合だけ実行する。

- ローカルの必須チェックが成功している
- 実動作確認が期待どおりである
- 必須CIが成功している
- コンフリクトがない
- 必須レビューとブランチ保護を満たしている
- リポジトリで許可されたマージ方式を使用できる

CIが存在しない場合は、承認ゲートでその前提を提示済みであり、ローカル検証が十分な場合だけ進める。pending、失敗、実行不能を成功扱いしない。

マージ方式はリポジトリ設定と既存履歴に合わせる。ブランチ削除は承認済みの場合だけ行う。マージ後はIssueのclose状態と既定ブランチへの反映を確認する。

## 停止時の報告

マージ条件を満たさない場合はPRを残し、次を報告する。

- 停止した工程
- 失敗・未完了のチェック
- PRとIssueの状態
- ユーザーまたはレビュアーに必要な対応
