# 変更の計画・実装・公開

1件の変更について、ステアリング作成、1回の承認、実装、検証、承認されたGitHub操作までを進める。文書体系の初期化や一般的な文書規則の定義は `$dev-docs` の責務とし、このスキルからその本文を読み込まない。

## 出力言語

- ユーザーが別の言語を明示しない限り、日本語で出力する。
- ステアリング、承認依頼、進捗報告、完了報告、Issue、PRの説明文を日本語で作成する。
- コード、コマンド、パス、API、型名、識別子、製品・サービスの正式名称は、正確性のため必要な原表記を維持する。
- 既存文書を更新するときは、対象文書の指定言語を優先する。指定がなく、新規作成または全面更新する文書は日本語に統一する。

## 入力と完了条件

- 引数には追加・変更・修正したい内容を受け取る。内容が無ければ、目的と期待結果だけを確認する。
- 完了条件は、承認済みの受け入れ条件、必要なテスト、実動作の確認、承認された公開操作の完了とする。
- Issue、push、PR、マージは、承認ゲートで具体的に提示して承認されたものだけ実行する。

## コンテキスト方針

- `docs/**` と完了済み `.steering/**` を一括で読まない。
- 最初に `AGENTS.md`、文書とコードのファイル一覧、パッケージマニフェスト、主要設定を確認する。
- 文書は見出しや検索結果から対象を絞り、今回の判断に必要なセクションだけ読む。
- `docs/ideas/initial-requirements.md` は、`AGENTS.md` が真の情報源に指定する場合、または変更がプロダクトの目的・範囲に影響する場合だけ読む。
- コードは識別子、利用箇所、テストを検索してから対象ファイルを読む。
- 不足情報が判明したときだけ追加読込し、念のための全件読込はしない。

文書の選択目安:

- ユーザー向け機能・受け入れ条件: product requirements
- 振る舞い・API・データモデル: functional design
- 技術選択・境界・依存方向: architecture
- 配置・公開境界: repository structure
- コマンド・テスト・Git規約: development guidelines
- 新しいドメイン用語: glossary
- フェーズや提供範囲: roadmap

## 実行手順

### 1. 前提を確認する

- `AGENTS.md`、`docs/`、`.steering/`、Git状態を読み取り専用で確認する。
- 文書駆動の前提が未整備なら、コードを書かずに `$dev-docs init` を案内する。
- 未コミット変更はユーザーのものとして保持する。勝手にstash、commit、破棄しない。安全に分離できない場合だけ状況を説明して停止する。
- GitHub連携、既定ブランチ、利用可能なラベル、CI、マージ方式は必要な範囲で読み取り確認する。

### 2. 変更と影響を分析する

- ユーザー要求、現行仕様、対象コード、関連テストから変更範囲を決める。
- 永続文書を更新するのは、承認後も残る製品契約や基本設計が変わる場合だけとする。
- 既存仕様どおりのバグ修正、内部リファクタリング、テスト追加、局所的な実装詳細では永続文書を更新しない。
- 更新する場合は所有文書を1つに定め、他文書へ同じ説明を複製しない。

### 3. ステアリングを作成する

`AGENTS.md` の規則を優先する。規則がなければ `.steering/YYYYMMDD-development-title/` に次を一括作成する。

- `requirements.md`: 目的、スコープ内外、受け入れ条件、制約
- `design.md`: 実装判断、変更箇所、リスク、テスト方針、永続文書の更新対象
- `tasklist.md`: 実装・テスト・動作検証・文書更新のチェックリスト

3ファイルで文章を使い回さない。要求は設計から参照し、設計説明をタスクリストへ転記しない。`tasklist.md` は細かな作業ごとに編集せず、計画変更時と完了時にまとめて更新する。

### 4. 1回だけ承認を得る

次を短く提示して停止する。

- 開発タイトルとステアリングパス
- requirements、design、tasklistの要点
- 更新する永続文書と理由。無ければ「更新なし」
- 主要タスクと検証方法
- 実行予定の外部操作: Issue、ブランチ、push、PR、マージ、ブランチ削除

外部操作は実際に行うものだけ列挙する。GitHubが利用できなければ、スキップする工程を明記する。承認は提示した範囲にだけ有効とし、追加の外部操作や破壊的操作には流用しない。

修正要望があればステアリングを直して再提示する。承認されるまで、コード変更、Issue作成、ブランチ作成、永続文書更新を行わない。

### 5. 承認内容を実行する

1. GitHub操作が承認されていれば、ここで初めて [GitHub公開手順](references/github-publish.md) を読み、Issueと作業ブランチを準備する。
2. 永続仕様を変える場合は、承認済み内容を該当文書へ先に反映する。
3. ステアリングに従って実装し、変更ロジックに対応するテストを追加・更新する。
4. `AGENTS.md`、マニフェスト、既存CIから検証コマンドを特定し、関連テストから全体チェックへ広げる。
5. CLI、API、ブラウザなど変更に合った実動作を確認し、コマンドと観測結果を記録する。
6. 計画変更があればステアリングへ反映し、完了時に `tasklist.md` を一度更新する。
7. commit、push、PR、マージが承認されていればGitHub公開手順に従う。

設定が存在しない検証ツールを勝手に追加しない。失敗したチェックは原因を修正して再実行し、実行不能な項目は理由を報告する。

### 6. 完了を報告する

- ステアリングパス
- 実装結果と主要な変更箇所
- 更新した永続文書
- lint、型、テスト、実動作の結果
- Issue、PR、マージ結果
- 未完了事項や判断が必要な点

同じ説明をIssue、PR、完了報告へ再掲しない。リンクと差分要約を中心にする。

## 停止条件

次の場合は安全に進められる範囲まで実行し、PRまたは作業ブランチを残して停止する。

- 承認済み要求を変える必要が生じた
- ユーザーの未コミット変更と安全に分離できない
- 必須のlint、型、テスト、実動作確認が失敗または実行不能
- CIが失敗・未完了、コンフリクト、レビュー必須、ブランチ保護でマージできない
- 承認されていない外部操作や破壊的操作が必要になった

## 守ること

- `AGENTS.md` のプロジェクト固有規則を優先する。
- `main`や既定ブランチへ直接コミットしない。
- `git push --force`、`git reset --hard`、ユーザー変更の破棄を行わない。
- 明示したファイルだけをstageし、機密情報が含まれないことを確認する。
- 品質チェックと実動作確認が完了しない状態でマージしない。
- 永続文書は基本設計の変更時だけ更新し、ステアリングの内容を転記しない。
