# 文書駆動開発の整備

永続的な仕様を `docs/`、作業単位の仕様を `.steering/` に分けて整備する。
このスキルは文書体系の初期化・監査・更新規則を担当する。機能の実装、テスト、GitHub Issue、PR、マージは担当せず、必要なら `$add-feature` を案内する。

## 出力言語

- ユーザーが別の言語を明示しない限り、日本語で出力する。
- 生成・更新する永続文書とステアリング、監査結果、承認依頼、進捗・完了報告を日本語で作成する。
- コード、コマンド、パス、API、型名、識別子、製品・サービスの正式名称は、正確性のため必要な原表記を維持する。
- 既存文書を部分更新するときは文書全体の言語を維持する。新規作成または全面更新では、ユーザーの指定がない限り日本語に統一する。

## モード

- 引数なし: `AGENTS.md`、`docs/`、`.steering/` の配置だけを確認し、現状と不足を報告する。ファイルを変更しない。
- `init`: 既存ファイルを保護しながら、必要な永続文書、`.steering/`、`AGENTS.md` を初期化する。
- `audit`: 文書の重複、欠落、真の情報源、更新条件を監査し、改善案を報告する。明示的に更新も依頼された場合だけ編集する。
- `update`: ユーザーが指定した文書、または明示された仕様変更に関係する文書だけを更新する。

作業単位のステアリング作成や実装は `$add-feature` に委ねる。

## コンテキスト方針

- `docs/**` や完了済み `.steering/**` を一括で読まない。
- 最初に `rg --files` で配置を確認し、`rg -n '^#{1,3} '` などで文書の見出しを確認する。
- `AGENTS.md`、ユーザーが指定した情報源、今回の判断に必要な文書・セクションだけを読む。
- `docs/ideas/initial-requirements.md` は存在するだけでは常時読まない。`init`、要求の起点確認、または `AGENTS.md` が真の情報源に指定している場合だけ読む。
- 過去の `.steering/` は、現在の変更と直接関係するものだけ読む。
- 情報不足が判明した時点で追加読込し、念のための全件読込はしない。

真の情報源は、明示されたユーザー要求、`AGENTS.md` に記載された優先順位、現行の永続仕様、初期要求メモの順に解決する。既存プロジェクトでは、初期要求メモを自動的に最新仕様とみなさない。

## 実行手順

### 1. 状態を把握する

次を読み取り専用で確認する。

- `AGENTS.md` の有無と文書規則
- `docs/` と `.steering/` のファイル一覧
- README、パッケージマニフェスト、主要設定ファイル
- 既存文書の見出しと、重複・空文書・明らかな不整合

既存文書を無断で作り直さない。`init` では不足分を作成し、既存文書は明示的な更新依頼がある場合だけ変更する。

### 2. 作成・更新対象を選ぶ

`init`、`audit`、または永続文書を変更するときだけ [文書カタログ](references/document-catalog.md) を読み、各情報の所有文書と更新条件を決める。

- 内容を持たない文書をファイル数合わせで作らない。
- 同じ説明を複数文書へ複製しない。所有文書に記述し、他文書から参照する。
- 基本設計や永続的な契約が変わらない修正では、永続文書を更新しない。

### 3. アーキテクチャ選択を確定する

`architecture.md`、アーキテクチャを含む `functional-design.md`、境界・依存方向を定める `repository-structure.md` などを新規生成または実質的に変更するときだけ、この手順を実行する。

1. ユーザー要求、既存コード、既存文書から確定済みの設計を抽出する。
2. 未確定で実装や文書構成に影響する選択がある場合だけ [アーキテクチャ選択](references/architecture-decisions.md) を読む。
3. 関係する選択肢を2〜3個に絞り、推奨案を先頭にして影響を1文ずつ示す。
4. 質問は最大3件にまとめ、**1回だけ**ユーザーへ選択式で承認を求めて停止する。
5. 選択済みの内容、既存構成をそのまま文書化する場合、表現や章立てだけを変える場合は承認を求めない。

利用可能なら選択入力用のツールを使い、使えなければ短い番号付き選択肢を提示する。ファイル単位、章単位、図表単位の承認は求めない。承認後は選択を `architecture.md` に記録し、必要ならADRにも残す。

### 4. 文書を一括作成・更新する

アーキテクチャ選択が必要なら承認後に、不要ならそのまま、対象文書をまとめて作成・更新する。

- `product-requirements.md`: 何を、誰のために、どの条件で作るかを書く。
- `functional-design.md`: 安定した振る舞い、ユースケース、外部契約、データモデルを書く。
- `architecture.md`: 技術選択、実行構成、境界、依存方向、横断的制約を書く。
- `repository-structure.md`: 実ファイル一覧ではなく、安定した配置・公開境界の規則を書く。
- `development-guidelines.md`: 実行コマンド、コーディング、テスト、Git運用を書く。
- `glossary.md`: 意味の合意が必要なドメイン用語だけを書く。
- `development-roadmap.md`: フェーズ、順序、完了条件を書く。個別タスクの進捗は書かない。

図は関係を文章より明確にできる場合だけ、所有文書内へMermaidで記載する。独立した図表集や例示目的だけの図は作らない。

### 5. AGENTS.md を最小限更新する

`init` では `AGENTS.md` を作成または該当箇所だけ更新し、次に限定する。

- ステアリングの配置、命名、必須ファイル
- 真の情報源と文書の参照優先順位
- 確定した技術スタックと実行・検証コマンド
- プロジェクト固有の重要な境界・禁止事項
- 詳細な文書プロセスは `$dev-docs` に従うという参照

このスキル本文、一般論、各文書の長い要約を `AGENTS.md` へ転記しない。

### 6. 整合性を確認して報告する

- 文書間で同じ決定が矛盾していないか確認する。
- 相対リンク、ファイル名、コマンド、用語を確認する。
- 作成・更新したファイル、採用したアーキテクチャ選択、未確定事項を簡潔に報告する。
- 文書生成後に実装を自動開始しない。

## ステアリングの契約

プロジェクトの `AGENTS.md` に別規則がなければ、作業ごとに `.steering/YYYYMMDD-development-title/` を作り、次の3ファイルを置く。

- `requirements.md`: 今回の目的、範囲、受け入れ条件、制約だけを書く。
- `design.md`: 要求を再掲せず、実装判断、影響範囲、永続文書の更新対象を書く。
- `tasklist.md`: 実行項目と完了条件だけを書く。設計説明を再掲しない。

作業中の細かな進捗は実行時の計画で管理し、`tasklist.md` は計画変更時と完了時にまとめて更新する。

## 守ること

- 現在のユーザー要求とリポジトリ固有の `AGENTS.md` を優先する。
- 既存文書やユーザーの変更を無断で上書きしない。
- 選択式の承認は、未確定のアーキテクチャ判断を文書へ確定するときだけ求める。
- 文書作成そのもの、非アーキテクチャ文書、ファイルごとの確認では承認を求めない。
- 永続文書、ステアリング、Issue、PRで同じ文章を重複させない。
