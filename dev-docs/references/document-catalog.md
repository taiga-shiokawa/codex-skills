# 文書カタログ

`dev-docs init`、文書監査、永続文書の更新対象を決めるときだけ参照する。

## 情報源の優先順位

1. 現在のユーザー要求と明示的な決定
2. `AGENTS.md` に記載されたプロジェクト固有規則
3. 現行の永続仕様
4. 承認済みADR
5. 初期要求メモと過去のステアリング

初期要求メモはプロジェクトの起点であり、常に最新の仕様とは限らない。現行仕様と矛盾する場合は勝手に統合せず、差分を報告する。

## 永続文書の所有範囲

| 文書 | 所有する情報 | 読む・更新する条件 |
|---|---|---|
| `product-requirements.md` | ビジョン、対象ユーザー、課題、製品スコープ、機能・非機能要求、成功条件 | ユーザー価値、提供範囲、受け入れ条件が変わる |
| `functional-design.md` | 安定したユースケース、振る舞い、画面遷移、外部契約、データモデル | API、データ、主要フロー、ユーザー向け挙動が変わる |
| `architecture.md` | 技術選択、実行・配備構成、モジュール境界、依存方向、横断的制約 | 技術、境界、依存、性能・セキュリティ方針が変わる |
| `repository-structure.md` | 安定したディレクトリ責務、配置規則、公開境界 | 新しい配置規則やモジュール境界が必要になる |
| `development-guidelines.md` | 開発コマンド、命名、コーディング、テスト、Git、レビュー規則 | チームの反復可能な開発方法が変わる |
| `glossary.md` | 意味の合意が必要なドメイン語とコード上の対応 | 新しい重要語、意味変更、命名衝突がある |
| `development-roadmap.md` | フェーズ、実行順、完了条件、主要依存 | 製品計画やフェーズ境界が変わる |

`init` の標準文書は `product-requirements.md`、`architecture.md`、`development-guidelines.md`、`development-roadmap.md` とする。次は必要な永続情報がある場合だけ作成する。

- `functional-design.md`: 複数の主要フロー、API、永続データ、画面遷移を設計する場合
- `repository-structure.md`: READMEやフレームワーク既定だけでは配置・境界を判断できない場合
- `glossary.md`: 一般語では表せないドメイン語や、コードとの対応が必要な場合

既存プロジェクトが7文書を採用済みなら維持する。空の見出しや一般論で文書を埋めない。

## 読み込みルーティング

- まずファイル名と見出しを見る。
- ユーザー向けスコープなら product requirements を読む。
- 振る舞い、API、データなら functional design を読む。
- 技術、境界、依存なら architecture を読む。
- 配置判断なら repository structure を読む。
- コマンド、テスト、Gitなら development guidelines を読む。
- 用語だけなら glossary を読む。
- フェーズや順序なら roadmap を読む。

複数領域にまたがる場合も、各文書の関係する節だけ読む。

## 更新しない例

- 既存仕様どおりのバグ修正
- 公開契約を変えない内部リファクタリング
- テストの追加・整理
- 同じ配置規則内でのファイル追加
- タスクの細かな進捗
- 一時的な調査結果

これらは必要ならステアリングやコードコメントへ残し、永続文書へ複製しない。

## ステアリングの所有範囲

- `requirements.md`: 今回の目的、範囲、受け入れ条件、制約
- `design.md`: 今回の実装判断、影響範囲、リスク、検証方針
- `tasklist.md`: 実行順と完了状態

背景や要求を3ファイルへ繰り返さない。Issueは要求の短い要約とステアリングへの参照、PRは実装差分と検証結果に限定する。
